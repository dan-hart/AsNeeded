# 1.2.0 stabilization and feature freeze

Effective **October 27, 2026**, at the maintainer's direction. Preserve the original vision: private, calm, dependable as-needed medication tracking, with especially easy dose recording. Remaining work is testing, reducing bugs, and refining the experience people already know.

## Baselines and scope

- Public comparison: **1.1.2 (296)**. App Store Connect currently reports1.1.2 as `READY_FOR_DISTRIBUTION`; the 1.1.2 Git tag also records build 296. The 1.1.3 tag is not proof of a public release.
- Frozen feature baseline: **1.2.0 (309)**, already approved for internal and external TestFlight testing. Existing optional interval/rolling 24-hour quantity limits, next-dose alerts and the implemented UX/accessibility corrections stay in scope for stabilization. The removed Private Questions feature stays removed.
- New features, additional integrations, new insight types, broad navigation/visual redesigns, speculative architecture work and unrelated dependency upgrades belong after 1.2.0. An older plan or wishlist does not authorize adding them to this release. Only an explicit maintainer decision reopens feature scope.
- Allowed changes: the smallest reproducible bug fix, meaningful regression test, accessibility correction, clearer wording, removal of friction or distracting decoration, necessary release/signing repair, and accurate release documentation. Tie refinements to an observed issue or a concrete continuity problem.
- Preserve the ease of Add → Log → History, the familiar four tabs, existing user preferences and font choices, and optional setup. Do not turn optional limits/alerts into onboarding requirements or make basic recording depend on Shortcuts.

## Stabilization order

1. **Data correctness and preservation.** Reproduce and address dose-event/stock partial-save behavior; test repeated actions and retries, edits/deletes/Undo, units and fractional quantities. Confirm upgrades, migration, backups/import/restore and settings do not lose or duplicate records.
2. **Existing daily flows.** Compare adding/editing a medication, logging now/backdated, reading History/notes, reviewing Trends, reminders/refills and settings against 1.1.2. Keep the task recognizable and at least as easy to complete.
3. **Timing and delivery.** Exercise optional limits independently/together, rolling 24-hour and midnight boundaries, missing/incompatible units/history, editing/deleting records, permission denial/re-enabling and private notification content. Check scheduled reminders separately from next-dose alerts.
4. **Interaction and accessibility.** Verify short tap/long press/scroll separation, native toolbars, save/cancel/discard and error recovery, large text/custom fonts, VoiceOver/Voice Control/keyboard access, light/dark, Increase Contrast, Reduce Motion and Reduce Transparency.
5. **Secondary surfaces and release mechanics.** Test widgets/Live Activities, Siri and paired Watch on real devices, including offline/reconnection/cancellation. Keep signing/configuration repairs separate from app behavior and preserve other projects' signing assets.

## Release gate checklist

Record device/runtime/build, scenario, expected/actual result and a reproducible defect for failures. Keep patient records, contacts, signing material and raw private logs outside Git. Use synthetic fixtures and disposable backups for destructive scenarios.

- [ ] No unresolved known release-blocking defect involving lost/duplicated doses, incorrect units/stock/timing, corrupted upgrades or inaccessible core actions. Investigate the event/stock transaction gap before sign-off; successful unit tests do not dismiss it.
- [ ] Existing 1.1.2 data survives an upgrade to the candidate and repeated launches, with medications, dose history, notes, quantities, preferences and optional configuration intact.
- [ ] Fresh install and legacy/current/mixed/restart migration scenarios have deterministic coverage. Classify and resolve existing fixture/cache/permission/default-key test failures; do not hide them as “pre-existing” or weaken assertions to make a green run.
- [ ] Add, edit, log, backdate, Undo, History edit/delete and cancellation have correct totals and recovery behavior. Save failure must not invite blind duplicate logging.
- [ ] Public-version continuity review has been completed for each core flow. Record extra steps, unfamiliar labels, displaced actions and surprising default changes. Simplify or revert unnecessary changes while preserving accessibility fixes.
- [ ] Physical notification privacy/delivery and opt-out/replacement behavior are verified, including background/terminated app states. Paired Watch and actual widget/Live Activity scenarios are checked or explicitly excluded from claims with a release decision.
- [ ] Representative small iPhone, larger iPhone and iPad checks cover normal/accessibility text, long names, keyboard, display settings and assistive operation; no clipped critical names/units or unreachable actions.
- [ ] Relevant regressions pass; broader checks have every failure accounted for. Test-runner launch failures and incomplete runs are not passes. Re-test changed paths after a fix and run broader checks once its scope warrants them.
- [ ] Final archive/export versions, dependency revisions, signatures, What to Test notes, internal/external availability and upgrade install are verified on the exact release candidate. No public submission is implied by TestFlight approval.

The goal is zero known release-blocking bugs and strong evidence, not a promise that software has no undiscovered defects. The target remains release before the end of 2026; defer scope rather than compressing necessary stability work.

## Bug-fix record

For each stabilization change, record: reproducible issue; whether it exists in 1.1.2, was introduced for 1.2.0, or is still unconfirmed; smallest correction; regression/interaction evidence; remaining risk. Keep deferred feature ideas separate from release blockers. No new UI or snapshot-test target is required; use focused behavior tests and honest rendered/manual evidence.

## First stabilization triage, October 27

A read-only standalone check compiled the actual `UserDefaultsKeys.swift` and executed the existing exactly-one-reset-category contract. It reproduced three unclassified keys: `storage.schemaVersion`, `migration.archivedLegacyMedicationsPath` and `migration.archivedLegacyEventsPath`. No defaults or stored records were changed. Their preservation/reset semantics need review before a correction; this is not yet fixed or waived.

The optimized one-worker DataStore suite stalled without producing test results and was interrupted. That run is not a pass. Its suite setup also shares a fixed storage identifier and global defaults; deterministic isolation/serialization needs review before relying on a broader run. These findings join the existing stability queue; they do not expand feature scope.
