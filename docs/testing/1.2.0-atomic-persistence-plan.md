# 1.2.0 atomic persistence stabilization

October 28, 2026. Authorized scope: dose/stock save recovery, import rollback, removal of all Live Activities, and a non-destructive upgrade check on the attached iPhone. No new product features.

## Storage analysis

- Keep `medications.sqlite3` and `events.sqlite3`, their App Group, model schema, and legacy migration intact.
- Add a versioned private undo journal (`pending-data-transaction.json`) and an advisory lock file in the same storage directory. These are recovery metadata, not replacement databases. Fresh/older installations need no conversion when no journal exists.
- Serialize app/widget writers using the same file lock, acquired without blocking the main thread. Load fresh persisted records while holding it; cached views are not authoritative for quantity calculations.
- Before any multi-store write, atomically persist and flush an undo record containing only affected medication/event records and IDs, plus the previous values of importable settings when relevant.
- Apply changes through Boutique, preserving the existing database format and cache observation. Clear the journal only after every required write/settings application succeeds. Do not swallow partial import errors.
- On ordinary failure, roll back before reporting failure. On interruption/cancellation or failed rollback, retain the journal; subsequent reads/writes and startup must recover it before proceeding. Invalid/unknown journals fail closed and remain recoverable.
- Normal dose transactions journal changed records only; replacing an import necessarily protects the entire replaced set. Do not copy or rename live SQLite/WAL files.
- Route logging, History edits/deletes, Undo, Siri, widgets and Watch saves through the shared owner. Update notifications/backups only after a completed mutation. Validate finite positive doses and compatible stock units; do not infer unit conversions.
- Repeated saves of the same event ID must not deduct stock twice. Shared locking prevents simultaneous surfaces calculating from the same stale quantity.

## Verification

1. Reproduce stock/event partial failure and failed replacement import with deterministic injected write faults against isolated SQLite stores.
2. Cover failure before journal creation, after medication writes, during event writes, before commit, and failed rollback; reopen after interruption and prove recovery/idempotency.
3. Exercise fractional quantities, untracked stock, mismatched units, repeated IDs, edit/delete/Undo, concurrent writers, import merge/replace and settings preservation.
4. Run focused regressions, then the full plan. Inspect result bundles; stalled launches are not passes.
5. Remove Live Activity creation/update/rendering, widget registration, support key and obsolete tests/active documentation. Retain the old attribute decoding shape solely to end existing activities on launch. Preserve ordinary widgets and notifications.
6. Build a new coherent 1.2.0 candidate. Back up/compare existing device data privately where supported, install over the current app without deletion/downgrade, restart, and run synthetic recovery/upgrade fixtures on hardware. Report the actual starting version; do not claim a public 1.1.2 binary upgrade if the phone already runs 1.2.0.

## Compatibility and remaining limits

Older releases ignore the recovery metadata and cannot recover an interrupted newer transaction. Do not downgrade with a pending journal. File locking protects cooperating writers in this candidate; it cannot coordinate an unrelated old executable. Existing records and legacy archives remain unchanged when no mutation is requested. Raw private device data, hashes/receipts and signing artifacts stay outside Git.
